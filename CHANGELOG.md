# Changelog

## Unreleased

- `chat.new` gives the session `plain_look` (no status bar, mouse, the pane's title on the tab), as a session made any other way should have. `chat.lacking_look()` names the sessions under a prefix whose status bar is still on, so a session made by hand or by a restore can be given it. A restored session showed tmux's green status bar in its tab.
- `iterm.doubled_clients()`: each tmux session that more than one plain iTerm2 client shows, so the same session is open in two tabs, with its newer clients (terminal, pid, creation time), oldest left out. An iTerm2 that restores two saved tabs of one session when it starts makes this. A control-mode client and a client outside iTerm2 (an ssh login, another terminal app) are not counted. `iterm.detach_client(tty)` detaches one, which closes its tab and leaves the session running.
- `config.mcp_server_shapes()`: what a change to each MCP server's definition can mean to a running session, as fingerprints of the whole definition and of the definition without Python's `-P` flag, and the top package a `python -m` server runs. It never returns the arguments or the environment, which can hold tokens. `config.mcp_change_affects(then, now, folder)` says why a change changes something for a session working in `folder`, or None: a server it never loaded changes nothing, a removed one does, and a change that only adds or removes `-P` matters only when the folder holds the server's top package. A supervisor that restarted every session when one server gained `-P` restarted many that imported the same code either way.
- `update.tools_called(path, since, prefix=)`: the names of the tools a conversation called at or after a time, read from the end of its transcript and stopping at the first older record (at most `limit` bytes, 16 MiB by default). A tool that only appears in a call's text, such as a shell command that names it, is not counted. `update.tool_digests(source)`: a digest of each tool an MCP server module declares (`@<object>.tool()` functions), by name, and under `""` one of the code the tools share, each taken over the syntax tree so comments and layout do not count. Together they let a supervisor restart, after a server's tools change, the chats that called a changed tool, and leave the others for later. A chat keeps its server's old code until it restarts, and a resumed conversation keeps the tool definitions it loaded until it is compacted (`tools_held`), so a restart for a tool it never calls costs a whole reload and changes nothing it uses
- `chat.start_server_through_iterm(name, cwd)` creates a tmux session as the first session of a new tmux server, started by an iTerm2 window's command, so the server and its panes run in iTerm2's context instead of the context of a background job (one macOS consent prompt per app, and no scripting of iTerm2). `chat.server_running()` says whether a server runs. `chat.new` uses it when no server runs.
- `restack` moves every commit of each branch's own, not only its top one. The bottom branch moves every commit since it left the base, and each branch above every commit since the head the branch below had before it moved. A five-commit branch was rebuilt with only its last commit and stopped on a conflict, and a branch above with two commits lost the first. `--upstream` still names the commit a bottom branch sits on, for a branch whose base pull request merged with its commits rewritten, since a branch without it now brings those old commits along
- `claude_ops.sqlite_health`: whether an SQLite database inside a container is intact. An app with SQLite in a Docker volume can keep answering its health URL while a page of the file is damaged (the virtual machine under the container went down mid-write), failing only the queries that touch it. `quick_check_in_container(container, path)` runs `PRAGMA quick_check` read-only inside the container with the image's `sqlite3`, or its `python3` when there is no `sqlite3`, and answers intact, damaged (with SQLite's first lines) or not asked (the container is not running, the engine does not answer, the image has neither program), which is no observation and never a pass. `log_error_lines(container, since)` counts the lines of the container's log that carry SQLite's damage messages. `claude-ops sqlite-check <container> <path> [--since 10m] [--json]` exits 0 intact, 1 damaged, 2 not asked.
- `iterm.start_app()` opens iTerm2 when it is not running and waits until it answers, for an iTerm2 that something else ended. A running iTerm2 is left as it is ("skipped"), so nothing is stopped.
- `pr_changes`: a pull request git could not read is said, never shown as changing nothing. `changes` gives it `files` {} and `unread`, the reason (its branch is not in the folder, with the `git fetch` that brings it; the folder is no git working tree; the diff failed), `unread_lines` and `warnings` carry one line per such pull request (one line for all when more than three), and `changes(..., unread=problems)` appends the reason when gh could not list the pull requests at all. `fetch=True` (`--fetch`) fetches the missing branches once first. The cache holds one entry per repository and repository folder (the common `.git` of its worktrees), so a run from a folder with no refs no longer writes an empty listing that every later reader of that repository takes for ten minutes. A cached pull request that was unread is read again, and nothing is cached when gh failed. `claude-ops pr-changes` exits 2 when something could not be read and nothing matched, prints the unread lines to standard error with `--json`, and refuses a `.git` folder as `--git-dir`, where a diff of two refs prints nothing and exits 0. A run from a folder that was no repository had put 55 empty pull requests in the cache, and the next reader was told that no open pull request changed a file three of them changed
- `chat.diagnose` names Claude Code's usage-limit question (wait for the reset, or add funds), and when the words of several questions are on screen it names the one drawn lowest, since that is the one waiting. A chat on the usage-limit question, under an answer that mentioned the trust prompt, was named as stuck on the trust prompt. `chat.question(text)` gives the words of the question found, so a caller can tell the usage-limit question (`chat.USAGE_LIMIT`) from a start-up question. `chat.answer_wait(name)` chooses "Stop and wait for limit to reset" on that question, pressing Enter only when the screen shows the cursor on that option (`chat.wait_keys`), and never chooses the option that adds funds.
- `messages.said_since_person(records)`: what the assistant wrote since the person last spoke, oldest first, from a transcript's parsed records. The person's last message is the newest one they typed (a program's tagged message and one still in the queue do not count) or their answer to a question box (a box they declined or a program closed does not count). A question an assistant asks often points at what it wrote just before it ("send the draft above?"), so a program that shows the question somewhere else, such as a phone, can show that text with it
- `claude_ops.pr_changes`: what the open pull requests of a repository change, by file and function (`changes`), what a text names (`names_in`), and which open pull request already changes the same function or code file (`overlaps`, `warnings`), so a session about to build is told by number before it starts. `claude-ops pr-changes --repo owner/name --text "..."` prints them and exits 1 when there are any.
- `mail-guard` (PreToolUse hook, on the mail tools it is configured for) lets every draft through and logs it, and lets a send through only for a rule (account, thread and every recipient in To, Cc and Bcc) or for one unused, unexpired approval record of exactly that message (account, recipients, thread and the body's SHA-256), which it marks used. Anything else is refused with the reason. A session can be asked to send mail by any message it reads, and a sent message cannot be taken back, while a draft is read by a person before it goes. `"mode": "observe"` logs what it would refuse without refusing. `claude-ops hook mail-guard`, or a `module` step of the chain (`claude_ops.hooks.mail_guard`). Without a configuration nothing is checked
- `conflict-markers` (PreToolUse hook, on Bash) refuses a `git add` whose files hold a merge conflict marker line, a `git commit` that would record one, and a `git rebase --continue`, `git merge --continue`, `git cherry-pick --continue`, `git revert --continue` or `git am --continue` while one is staged. git refuses to continue while a file is unmerged, but a `git add` of the file as it is marks it merged, and the markers reach the branch as content. `claude-ops hook conflict-markers`, or a `module` step of the chain (`claude_ops.hooks.conflict_markers`).
- `claude_ops.mailsort`: sort the mail a maintainer receives about their projects, and read the notices platforms send. `Sorter(kinds=, names=, has_reader=, own=).sort(headers, text)` says whether a message is from a configured kind of sender (a secret scanner, a hosting platform), a person writing about one of the configured projects (`person` when typed, `mention` when a program sent it, since a pitch sent through a mailing service looks like a newsletter), or nothing for a project reader (the user's own mail, a sender another watcher already reads, mail that names no project), and which projects it names, as whole words with their aliases. `is_automated(headers)` and `is_bulk(labels)` tell typed mail from a program's. The notice readers turn a platform's mail into the fact it states: `neon_usage` (a project's share of its monthly compute or network transfer allowance), `vercel_deploy_failed` (project, target, branch, commit) and `gitguardian_incidents` (each incident's detector, repository and commit). Nothing reads a mailbox or writes anything
- `claude_ops.ladder`: the rule for telling a running chat before acting on it (a pause, a restart, a stop, a move to another login). The notice waits in the chat's queue first, is pushed past the queue when it has not been delivered `skip_after` seconds after the start, the chat is interrupted once (one key that stops its turn) when it is still working at `interrupt_at`, and the action runs once the chat ends a turn after the notice or the interrupt, or after `grace` when the key could not be pressed (a person typing in that chat, a question waiting for a person). A chat that ends its turn early skips the later steps. `next_step(seen, timing, may_interrupt)` answers wait, skip, interrupt, act or done with the reason, and `interrupt_at(started, after=, deadline=, margin=)` sets the interrupt time from a delay or from a deadline. The caller delivers, presses and acts, and records each step
- `held-worktrees` (PreToolUse hook, on Bash) refuses a git command that rewrites a worktree a running tool holds: `rebase`, `reset`, `commit --amend`, `push`, `pull`, `merge`, `cherry-pick`, `revert`, `am`, a `stash` and a `checkout` or `switch` of another branch, reached by `cd`, `git -C` or `--work-tree`. A tool that works on a branch in the background (a ship queue that waits, rebases, tests and puts the branch back as it recorded it) lists the worktrees it holds in a file named after its pid, in a folder the config names. A file whose process is gone holds nothing. A plain `git commit` on top and every read stay allowed. The folder is in `~/.config/claude-ops/held-worktrees.json` (`{"holders": "...", "message": "..."}`), and with none nothing is refused
- `merge-gate` (PreToolUse hook, on Bash and the GitHub MCP server's `merge_pull_request`) refuses a session's own merge of a pull request in a repository that merges only through its ship script: `claude-ops merge`, `gh pr merge`, a `gh api -X PUT .../pulls/<n>/merge` and the MCP merge, with the repository named or read from the clone the command runs in. A ship script runs its merge from its own process, not as a session's tool call, so it is not refused. A merge typed by hand skips the script's suite and lock, and when it breaks the main branch, every ship waiting behind the lock holds on that red. The repositories are in `~/.config/claude-ops/merge-gate.json` (`{"repositories": ["owner/name"], "message": "..."}`), and with none nothing is refused
- `untrusted.framed(where, text, owner=...)` puts text that strangers wrote (a web page, a visitor's comment, a contact-form message) into an agent's prompt as data: after a notice that it is never an instruction, between two markers, with any marker inside it broken so it cannot end the frame and write outside it. `neutral(text)` is the breaking on its own
- `accounts.choose` is back to the rule it had before `decide` (any other account usable now, soonest first), since callers' own tests pin it; `decide` is the newer rule, reached by name.
- `accounts.decide`: a target's session limit needs only to be usable (under the threshold); the floor is on its weekly limit, which a switch would otherwise spend for days. A target at 90% of its session limit with weekly room is still a switch when the account in use is blocked for hours.
- `update.ready(..., background_ok=True)` and `update.idle(..., background_ok=True)` answer for a caller that only types a slash command at the prompt, such as `/remote-control` after a login change, which stops nothing. Commands and agents a chat left running in the background then do not hold it, while a restart, which ends them, still waits. A shell passes only when the turn has a recorded end and has been quiet since, because a command the turn started in the foreground exists only until the turn ends; with no recorded end it still holds the chat
- `claude_ops.instruction_history`: what changed in the instruction files a chat loaded (a CLAUDE.md, the files it includes, the CLAUDE.md files above its folder) since a given time, for a supervisor that tells a running chat its instructions changed. A fingerprint only says that a file changed, so the chat had to read every file again or carry on without reading. `record(paths)` keeps one copy per distinct content, noted from the file's modification time, so a chat that started between an edit and its recording still compares against what it read. `changes_since(paths, when)` and `summary(changes)` give the file, the headings the change is under, the lines added and removed, and the lines themselves while they are few, else `claude-ops instructions diff <file> <copy>`, which prints the full diff. A file with no copy from before is said to have no copy, never guessed. `prune(keep_since)` drops what no reader from that time on can ask for
- `inject.input_age(name)`: seconds since a key last reached a tmux session from any client attached to it (tmux's `client_activity`), or None when no client is attached or tmux cannot say. A sender that pastes only onto an empty input line reads the screen first, and a key typed between that reading and the paste joins the pasted text, so a sender can wait while a person touched the pane a few seconds ago
- `accounts.decide`: the action for the account in use, decided against every account's usage, never from its own alone. A block on the session limit alone that resets within the hour is waited out (`pause`), an account with room on both limits is switched to with the most weekly room first, and when no account has room the wait is for the earliest reset that gives some, naming the account to switch to then. Before, `choose` took the first other account usable now, so one at 97% of its weekly limit was switched to in place of a session limit 43 minutes from its reset, and the switch spent that account's last weekly share for days. `choose` is now `decide`'s switch target.
- `project_board.Board(..., public=, description=)`: make the project public or private and set its short description. `ensure()` writes either only when it differs from what the project says, and None (the default) leaves it as it is. A new project starts private, so a board meant for anyone to read says `public=True`
- `claude_ops.gmail.Mailbox.message` also returns `internalDate`, Gmail's own arrival time for the message as a string of epoch milliseconds (None when the response omits it). A watcher that only acts on messages newer than the last one it saw needs the arrival time, not the Date header a sender sets, which can be wrong or arrive out of order; the metadata request already carried it, so this adds no call
- `iterm.bind_chat_keys(send_hex)` gives every iTerm2 tab that shows a tmux session named with a prefix (`claude-` by default) key bindings that send bytes, as that session's own setting, so only those tabs have them and their profile and other settings stay. `{"cmd+f": [0x0f, 0x2f]}` makes Cmd+F send Ctrl+O and then "/", which opens Claude Code's transcript search in fullscreen mode, where the conversation is not in the terminal's scrollback and iTerm2's own search finds only the screen. A tab that has the bindings already is left alone, and `apply=False` only names the tabs that lack them. `hex_bindings` writes the key map entries (the codes are joined with spaces, because iTerm2 splits a binding's codes on spaces only and sends just the first of codes split by newlines), and `key_string` names a key combination as iTerm2's key map does. `select_tty(tty)` makes the tab and session on a terminal the current ones of their window and answers the window's id
- `iterm.idle_shells(raw)` lists every iTerm2 session whose foreground is only its shell, with its window and the shell's working folder, so a program can see which projects have a window open with nothing running in it (what a chat leaves when it ends). `shell_windows` is now built on it
- `iterm.shell_windows(folder, raw)` finds every iTerm2 window holding a session whose foreground is only its shell, working in the folder or a folder inside it, as `{window id: [terminal]}`, and answers None when iTerm2 could not be read. That is what a chat or a program leaves in a project's window when it ends, and the window where a new session for the same folder belongs, so a program can open its tab there instead of opening another window. `shell_pid(ps_text)` reads whether a terminal runs only its shell, and `cwd_of(pid)` reads a process's working folder with lsof
- The documented ways to run a hook through the interpreter write `python3 -P -m claude_ops.hooks.<name>` (the README, and the run lines of `open_question`, `plain_voice`, `public_voice` and `protected_checkouts`). Without `-P`, `python3 -m` puts the session's working folder first on the import path, so a file there named like a module the hook imports would run in its place. `claude-ops install hooks` already writes `claude-ops hook <name>`, which does not have this problem. A test keeps every documented command isolated
- `no_session_links.redact(text)`: the text with every session link, Claude-Session trailer and id of a real transcript replaced by `<session id>`, for a program that copies text it did not write (messages, notes, logs) into a repository, an issue or a pull request, where no hook sees the write. An id that is not a transcript on this machine is kept
- `claude_ops.project_board.Board(repo, title, selects=, texts=)`: show a list of work kept somewhere else (a database, a queue) on a GitHub Project, one issue per record, without anyone typing a task twice. `ensure()` finds or makes the project and its single-select and text fields. `put(key, title=, body=, closed=, parent=, fields=, had=)` makes the record's issue match the record and returns the state it wrote, which the caller keeps and passes next time, so only what changed is written and an unchanged pass writes nothing. A single-select value the field lacks is added, keeping the options already used. `parent` nests the issue under another as a sub-issue. `prune(days)` takes closed items off the project (the issues stay). Each Board counts its writes, waits between them and stops at `budget` with `OutOfBudget`, because GitHub limits how fast one account may write. A failure part way through a record raises `BoardError` carrying what was written, so an issue is never made twice. `ignore_notifications()` stops the repository's notifications reaching the account that writes
- `go_public.go` takes `before_checks(repo, public)`, called once the scan has passed and before the pull request that adds the check, and only when that pull request is needed. A caller uses it for whatever the check needs in order to run at all, such as a self-hosted runner for a private repository whose hosted Actions minutes have run out (with `before_public` removing it again before the visibility change)
- `claude_ops.cron`: cron schedules read in a named time zone, for a loop that decides itself what is due. `due(expr, last, now, zone=)` answers the newest time the schedule names after the last run and at or before now, or None, and `previous(expr, at, zone=)` the newest at or before a time. The five usual fields with lists, ranges, steps and names, the `@daily` shorthands, and a `CRON_TZ=<zone>` prefix. A wall time a clock change skips fires at the instant after the jump, and one it repeats fires once. `parse` raises ValueError for a schedule that is not one, so a caller can refuse it when it is written
- `claude_ops.gmail.Mailbox.body(id)`: the message's text, for a watcher that has to read it and not only match on its headers. It returns the first text/plain part decoded (walking a multipart message), falls back to the text/html part with its tags stripped (script and style dropped, character references decoded, runs of whitespace collapsed), and returns an empty string when there is neither. It asks for the full message over the same token path as `message` and writes nothing to either file
- `go_public.go` refuses to make a repository public while a self-hosted runner is registered to it, since a pull request from a fork could then run its jobs on that machine. `before_public(repo, runners)` is called first and may remove them; a runner still there, or a list GitHub would not give (it needs admin rights), stops it. With `check_only`, or for a repository already public, the runners are reported, not refused. `go_public.self_hosted_runners(repo)` lists them, and the result carries `runners`
- `commandline.writes` expands a target's variables with those the line assigned (`D=/tmp/x && cat > $D/f <<EOF`), as `steps` and `git_invocations` already do. A target such as `$D/f` stayed literal and was read as a path under the current folder, so `public-voice` refused a scratch file outside every repository, written from inside a public repository's checkout, as if it were a file of that repository. A variable the line did not assign is still read as a path under the current folder
- `ask-what-you-need` keeps the turn going through `hookSpecificOutput.additionalContext` (exit 0) instead of exit 2 with the reason on stderr. Claude Code showed every exit-2 Stop as a red "Stop hook error", which read as a broken hook; feedback is labelled "Stop hook feedback" and keeps the same loop protections (`stop_hook_active`, and a cap on continuations). `ask_what_you_need.feedback(reason)` builds the output
- `claude_ops.gmail.Mailbox(token_file, client_file)`: search a Gmail mailbox (`search(query, max_results=)`, the same words as Gmail's search box) and read a message's headers, labels and snippet (`message(id, headers=)`), with the token file and OAuth client file a finished Google sign-in leaves on disk. It uses only the standard library and asks for a fresh access token once per Mailbox, so a scheduled watcher that makes one per run never holds an expired token and needs no browser. A refusal raises `GmailError` with its HTTP status. Each watcher that reads mail no longer carries its own copy of the token exchange
- `update.question_unreachable` and `update.ready` no longer say that a restart through an open question loses only the dialog. Claude Code writes a tool call to the transcript only once the call has returned, so an open question, and the reply above it, are on the screen only, and a restart through it loses both. Close the dialog first (one Esc returns the call, and the questions are then in the transcript), then restart
- `open-question` (`claude-ops hook open-question`, `claude_ops.hooks.open_question`): a session's open AskUserQuestion call, known from the moment it starts. Claude Code writes a tool call to the transcript only once it has returned, so a reader of the transcript saw no question while a box waited for an answer, only the records before it. The hook keeps the call's id and questions in a file per session on PreToolUse and removes it on PostToolUse, SessionStart and SessionEnd. `open_question(session, records)` reads it and gives None once the transcript holds the call's result, so a call that ended without a PostToolUse hook reads as closed too
- `iterm.tty_listing()`: every iTerm2 session's terminal with its window, read in one AppleScript call, or None when iTerm2 did not answer. Pass it as `raw` to `window_of_ttys` and `windows_of_ttys` to answer for many tmux sessions from one reading. Asking per session walks every window again, close to a second each, and when iTerm2 does not answer each question waits its whole 8 seconds, so a loop over eight sessions waited more than a minute
- `update.ultracode_of(transcript)`: whether ultracode was on, from the conversation's newest record of it (the `ultra_effort_enter` and `ultra_effort_exit` attachments, and the "Ultracode on" or "Ultracode off" that /effort prints). Claude Code keeps ultracode for the session only, so a resumed chat came back with it off. `chat.resume_command(..., ultracode=)` and `update.resume_line(..., ultracode=)` start the resumed chat with it on again through `--settings '{"ultracode":true}'`, beside the effort it ran on, and `restart_tmux`, `restart_iterm` and `restart_into_tmux` read it themselves. A chat with a settings file of its own keeps the file and is not given ultracode, since a second settings flag would replace it
- `restack --upstream COMMIT` (`restack(..., upstream=)`): the commit the bottom branch sits on now, so every commit after it moves onto the base, not only the top one. After the pull request below merged with its commits rewritten (a squash, or a merge queue that rebases), the old commits are not on the base, and a merge or a plain rebase brings them back to conflict with their rewritten copies. And each commit that stops on an add-only conflict is settled and continued, so a branch of several commits moves whole. A second conflicting commit used to stop it
- `mcp_park.put(servers, parked_path=)` keeps definitions in the parked file, replacing any of the same name, and returns the names whose definition changed. An installer that provides an MCP server not every session should start can keep its definition current there without adding it to the configuration, where every session would start it
- `chat.claude_command` takes `model` and `effort` (`--model`, `--effort`), so a chat can start on a model other than the settings' default, as `resume_command` already reopens one. With `settings` neither is added, since the settings file decides the model
- `commandline.without_heredoc_bodies(command)`: the command line with every here-document body blanked out, character for character, so each position still names the same place in the original line. A body is data (a commit message, a script written to a file), never shell words, so a hook that looks for a command word, or rewrites one in place, reads this instead of the raw line. A hook that rewrote every `open` outside quotes also rewrote the words "open Wi-Fi" inside a commit message
- `markdown.unwrap` is idempotent (`unwrap(unwrap(t)) == unwrap(t)`), so text it wrote is never read as wrapped again. A line longer than `MAX_WRAPPED` (120) is a paragraph already on one line, never a wrapped line, so the line after it is not joined to it. A second `unwrap-github` run found posts the first had rewritten and joined more of them
- `plain-voice --file PATH` checks the text in a file and exits 2 with the reason when it may not go to GitHub, for a script that posts with gh itself, where no hook sees a tool call. `plain_voice.check_text(text, cfg)` is the check on its own
- `update.newest_api_error(transcript)`: the API error a conversation's turn ended on, of any kind, when it is the newest message (Claude Code's `isApiErrorMessage` record, with its `error` kind and text). `update.stopped_on_api_error` now reads through it. `update.stopped_on_login_error(transcript)` answers it when the kind is `authentication_failed` ("Login expired · Please run /login"): such a session answers nothing until it is restarted with a working login, and this tells without reading its terminal, as `login_lost` does from a screen
- `plain-voice` (`claude-ops hook plain-voice`, a PreToolUse hook): refuses a pull request, issue, comment or release body with a paragraph broken across lines (GitHub shows every line break, so wrapped text reads cut mid-sentence) in a `gh` command, a `gh api` call or a GitHub MCP call, and saves the joined text to a file to send instead; it can also refuse phrases from a configured list, matched against the prose only. `markdown.unwrap(text)` joins the lines of each paragraph and list item and leaves code, tables, headings, quotes, HTML and trailers as they are; `markdown.wrapped` and `markdown.is_wrapped` say where. `claude-ops unwrap-github [--repo owner/name] [--apply] [--limit N]` (`github_unwrap.run`) rewrites what the user already posted that way
- `merge --dependency-bump` reads the diff: every package a manifest or lockfile moves must be one the title or body names and move within the level, and a package the diff adds, removes or moves unnamed (a transitive dependency across a major) is refused. The formats read are npm's, yarn.lock, Python's (pyproject.toml, requirements, uv.lock, poetry.lock, pdm.lock), Cargo's, go.mod and composer's (`dependency_bump.moves`). And the author must be a named updater, Dependabot or Renovate by the logins gh prints, or one given with `--bot LOGIN`, never any bot: every GitHub App with pull-request write is a bot, and a login starting `app/` passed before
- `mcp_containers.read()` raises when the process list cannot be read (`ps` exits non-zero), as it does when docker does not answer. A failed list read as an empty one made every container look like an orphan, the running sessions' included, and a caller stopping orphans would have stopped them
- `mcp-park` (`claude-ops mcp-park list|park|unpark|keep`, `claude_ops.mcp_park`) moves MCP server definitions between `~/.claude.json` and a parked file (`~/.claude/mcp-parked.json`, mode 0600), or park every configured server but some. Every session starts every configured server, so with many sessions open, servers they do not use still cost memory in each. `definitions()` reads both files, for building a session's own `--mcp-config` file. A definition reaches the parked file before the configuration loses it

Usage limits, a prompt that is too long, billing and an expired login are not transient (`NOT_TRANSIENT`), since asking again cannot help
- `claude-ops merge <number>` (`merge.merge_when_green`) merges a pull request only when every check on its current head has passed, waiting for checks still running. It reads the checks from gh's JSON, refuses a pull request with a failed check or with no checks at all (`--allow-no-checks` to merge one anyway), and merges with `--match-head-commit`, so a push between the check and the merge is refused by GitHub. Waiting and merging as two steps had let a pull request be merged with two test jobs red
- `update.idle` and `update.ready` look through background shells that only wait: a loop whose body is `sleep N` (`until <test>; do sleep 60; done`), followed by nothing or only commands that read and print, sitting in its `sleep` right now (`is_waiter`, `waiting_shells`, `command_lines`). Such a shell loses nothing when its chat restarts, because the next instance is told which background commands did not finish. A chat that kept a few of these running was never idle, so it was never restarted. `ready` reads the command lines itself; `idle` uses them when given
- `chat.diagnose` looks for a start-up question only in the last lines of the screen, and never while Claude Code's input box is there (`chat.input_box`). It matched the words anywhere, so a chat at its prompt whose conversation quoted "Yes, I trust this folder" read as stuck on the trust question, and `chat.at_prompt` never saw it ready
- The session index follows a conversation that moved to another folder: every record names the folder it ran in, and the newest one is the entry's `cwd`, on a full read and on an incremental one. It kept the folder of the first record, so a chat resumed elsewhere was listed under the folder it had left
- `sessions.build_index` writes the cache through a temp file of its own: with one shared name, two processes indexing at once renamed each other's file away and the second failed
- The test suite never reaches the tmux server of the person running it: a session-wide fixture unsets `$TMUX` and gives tmux a private `TMUX_TMPDIR` under /tmp. Inside a tmux pane, tmux follows `$TMUX` before `TMUX_TMPDIR`, so a test's `tmux kill-server` cleanup ended the real server and every session in it
- `inject.send_tmux` loads the text into the tmux buffer through stdin (`load-buffer -`). It passed the whole text as one `set-buffer` argument, and tmux refuses a command longer than about 16 KB with "command too long", so a long message never arrived and the error text was all the sender got
- `update.tools_held(transcript)`: the deferred tool definitions a conversation holds now, each tool as its newest load since the last compaction recorded it, with its description and argument names. A resumed chat keeps those until it is compacted, so a restart does not give it an argument a server gained in the meantime. Compare them with the server's tools before telling a chat its tools are current
- `update.restart_iterm` and `update.restart_tmux` (when it builds the resume line itself) pass the chat's current title as `name`, so a chat renamed after it started comes back under its new name. They passed the start flags' `-n`, Claude Code wrote it back as the chat's title, and the rename was undone. `update.title_of` and `update.remote_control_of` read the transcript from its end, so a long one is not read whole (two seconds for a 1.8 GB transcript, now a few milliseconds)
- The session index reads a transcript that grew only from where its last read stopped, and writes its cache only when something changed. The chats in use are the largest files, and reading a 100 MB transcript whole on each change took about a second. `sessions.rc_url` reads the same way, and `sessions.live_folders` asks `lsof` once for every process instead of once for each
- The iTerm2 listings (`inject.iterm_sessions`, `inject.send_iterm`, `update.screen_of`) skip a window iTerm2 keeps in its scripting model after it closed, whose tabs cannot be read. One such window made every listing fail, so no iTerm2 session was found at all; an error after the session was found is still raised
- `update.background_agent` also sees a workflow's agents, which write one folder deeper (`subagents/workflows/<run>/`), and counts a workflow as running between its phases while its journal is recent and it has no final state file. A chat running a workflow no longer reads as idle, so a restart does not end the run halfway
- `update.files_seen(transcript, since=None)`: each file the conversation wrote (Write, Edit, MultiEdit) or read whole, with the time of that result. Check it before telling a chat that a file it loads has changed, because a chat that changed the file itself already knows. Compare with the file's modification time to see whether someone else changed it afterwards
- `update.unfinished_background(transcript)`: the background commands a chat started that never got a task notification, with their command text, so a chat resumed after a restart can start again what it still needs. `update.last_start(transcript)` gives when the newest instance started, to pass as `since`.
- `inject` sends only into an empty input line: a half-typed message, a question on screen or a screen it cannot read answers `not-ready` (exit code 5) and sends nothing. `--force` still skips the checks
- `update.screen_of` reads a tmux pane with its styles and `update.plain_screen` drops the suggested next prompt Claude Code draws dim in an empty input line, so `empty_prompt` no longer reads a suggestion as text somebody typed. `chat.pane_text(styled=True)` keeps the codes, and `update.TYPED` names the typed-text answer
- `update.resume_line(..., name=...)`: the chat's current name replaces the `-n`/`--name` (and a named `--remote-control`) it started with, so a restart does not undo a rename.
- `update.model_of` reads the model and effort level a chat last ran on from its transcript, and every restart and `chat.resume_command` pass them on (`--model`, `--effort`), so a model or effort chosen inside the chat survives a restart. A chat started with `--settings` keeps the model its settings file names
- `update.restart_into_tmux` moves a chat from an iTerm2 tab into tmux shown in that same tab, and `update.restart_tmux` restarts a tmux chat inside its own pane. Neither opens a window
- `update.ready` puts every check on a chat in one place, adds `update.background_agent` (a background agent keeps a chat busy), and names a question waiting for the person instead of calling the chat "working"
- `update.remote_control_of` and `update.title_of` read a chat's Remote Control state and title from its transcript, so a restart keeps Remote Control
- `update.front_app(bundle_id=True)` gives the bundle id of the app in front
- `config.descendants(pid, procs)`, every process under one, so a window can be traced to the chat whose process made it
- `chat.in_tmux`, `chat.plain_look`, `chat.attach_line` and `chat.server_context`. A plain tmux session passes the chat's title to the terminal tab, so the tab no longer reads "cd (tmux)"
- `chat.claude_command` and `chat.resume_command` take `settings`, a settings file for that chat alone (`--settings <file>`), and a restart keeps the flag
