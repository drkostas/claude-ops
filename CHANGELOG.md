# Changelog

## Unreleased

- `clock-ahead` counts "by" as a deadline word only when the time follows it ("by 14:00", "by about 14:00"). An earlier fix took out the one phrase "by hand", but "by accident at 14:00", "by default at 14:00" and "by name at 14:00" had the same fault. In each the time belongs to "at", yet "by" sat within three words of it, so a past time a few minutes ahead of the clock went through unflagged. Any "by" that is not followed directly by the time is now ignored, so no phrase list is needed.
- `missing-names` (`claude-ops missing-names --base origin/main tests/test_x.py`) lists the names test files need that a base revision's modules do not have, before the files run there. A run that proves new checks fail on the base branch crashes instead when a check reads a name only the branch has (a new function, constant, module or parameter), and that crash proves nothing and is only seen after the run. This reads the files alone, in under a second a file, and names each missing module, name or argument with its line. It reads each imported module of the repository as it is at the base revision through `git show`, checks `module.name` reads, `from module import name` and the arguments of `module.f(...)` calls against it, and leaves out a use under `try` that catches the error, under `if hasattr(module, "name")`, an attribute the file sets itself, an alias the file rebinds, and a module whose names cannot be read from its text. Exit 0 when nothing is missing, 1 when something is, 2 on a usage error. It runs nothing, so a name a module makes only when it runs (through `globals()`, `exec` or `setattr` on itself) reads as missing, and the summary line names that form.
- `merge` explains a failed check with the words of that check's own run. A workflow that also runs when a pull request is edited runs again on the same head under the same name, and the head's checks then list both runs. The failure message matched words to a check by name and kept the first run the API listed, so a failed run could be printed with the summary of the run that passed beside it, and the stated reason contradicted the verdict it explained. Each failed check is now matched to its run by the run's id (the end of a GitHub Actions job's details address), and a check without an id falls back to the newest run of its name. `check_words` by name also takes the newest run rather than the first listed, and the check runs are read from every page, where a second page used to make the words come back empty. The verdict itself is unchanged, since it already reads every run and stops on any that failed. `merge.run_words` is the new part.
- `mail_guard` says when only the body differs. A send whose account, recipients and thread match an unused, unexpired approval but whose body hash does not was refused with the same words as a send nothing approved ("no unused approval matches this exact message"), so a session that had changed a word of an approved text could not tell that the text was the cause. Such a send is now refused with "an unused approval for this account, these recipients and this thread exists, but this body is not the approved one", and told to send the approved body exactly or ask for a new approval. The approval stays unused. Every other refusal keeps its words. `mail_guard._open_approvals` is the part.
- `answer-sizes` (`claude-ops answer-sizes --prefix mcp__<server>__`) reads Claude Code transcripts and says, per tool, how many answers it gave, the longest, the 99th percentile and how many were longer than `--limit` (20000 characters by default), over the last `--days` days. It keeps lengths only, never the text. Each answer is dated by its own transcript line rather than by its file, since a long-lived session's file is new while its first answers can be months old, and an MCP `{"result": ...}` wrapper is taken off before counting, since its escaping adds about a tenth. A measured maximum is what happened in the window, not a bound on what can happen, so it finds the tools worth a look and the code decides whether an answer is small. Each tool also gives `at_max`, how many answers share its largest length exactly, and the line says so when more than one does. Answers of real sizes have one largest, so several at exactly the same length are how a cut looks from the reader's side, and that maximum is the cut's length rather than a size. This needs no knowledge of any limit. `at_max_last` dates the newest answer at that length, since a window can hold a cut that was later removed, and a cut whose newest answer is weeks old is history rather than how the tool answers now.
- `email-reply` builds the reply to a Gmail thread and shows it, and sends it only with `--send`. A reply made by hand through an API goes wrong in three ways that the sender's own mailbox never shows: a body with bare line feeds reaches Outlook and Exchange as one paragraph (mail libraries turn CRLF back into LF inside the encoded body), a reply made against an older message or against the sender's own last message makes a thread that talks to itself, and a reply with only the reply headers reads as a new message. The command answers the newest message that is not a draft, refuses when that message was sent from the mailbox itself, and hand-builds the MIME (CRLF throughout, an RFC 2047 subject, `In-Reply-To` and `References` from the message answered, an attribution line and a quote). Showing is the default and sending needs the opposite flag, because the command puts mail in front of other people and cannot be taken back, so it is not a capability any caller should get as a side effect of a convenience. After a send the message is read back and checked on the decoded body, never on the base64 text around it, which passes while the body is still broken, and the command prints `VERIFIED` or lists what is wrong and exits 1. The body is read from a file, since an apostrophe inside a shell argument fails far from its cause. `Mailbox.thread`, `raw`, `raw_labels` and `send`, and `mail_reply.reply`, `build`, `newest_received` and `problems` are the parts.
- `raise-gate` is a Stop hook, and `claude-ops hook raise-gate` runs it. A session that uses tools it did not write is the only witness to their faults, since the tool's owner cannot see the call, but the cost of a fault (a refusal with an opaque message, a schema learned by retrying) lands on the session and the benefit of reporting it lands on everyone else, so by default nobody reports. The hook keeps a turn going when a call to a watched tool failed since the user last spoke and the final message has no line that starts with the heading (default `Raised upstream`) and names an item id or says `none` with a reason of at least two words. A watched tool is an MCP tool whose name starts with a configured prefix, or a Bash command that runs a configured program or `python -m` a configured module. An MCP tool counts on any error result, a command only when its output also holds one of the configured shapes, because a program may exit with a failure on purpose to report a finding. Results that hold an `ignore` shape (a call made before the tool's schema was loaded, a command another hook refused), ordinary shell errors, failing tests and git conflicts never count. A fault that exits 0 is not seen, since the failure flag is the only fact the transcript records about a result. It reads `--config`, `CLAUDE_OPS_RAISE_GATE_CONFIG` or `~/.config/claude-ops/raise-gate.json`, and with none nothing is held. It fails open and cannot loop (`stop_hook_active`). `raise_gate.check`, `faults`, `satisfied`, `raised_line` and `runs_watched` are the parts.
- `bearer_check.status(url, value, header=None)` asks an https address once with a bearer value and returns only its status and, when one is named, that one response header (for example `X-OAuth-Scopes`, which says what a GitHub token may do). It is for a job that makes a new access token and must learn whether the new one works and the old one no longer does, without the value reaching a log, an event or a message. The value is in no field, no `why` and no repr of the answer. A value that is empty or holds a space, a control or a non-ASCII character is refused, because a header built from it could carry a second header, and the refusal never repeats it. An address is held to `url_check.problem`. A redirect is never followed and is returned as its own status, since following it would send the value to an address the caller did not name. The timeout is a total for the whole answer. `bearer_check.Answer`, `status` and `value_problem` are the parts.
- `stray-refs` refuses a `git fetch` whose refspec names its own destination, and `claude-ops hook stray-refs` runs it. A refspec may carry a destination, so one typed line can store a ref for a branch a remote never had (`+refs/pull/7/head:refs/remotes/origin/pr-7`) or one for every open pull request (`+refs/pull/*/head:refs/remotes/mine/*`), and nobody meets either again, because neither is a branch any command lists and the line that made it was typed once. What a prune reaches is the whole question and it is two answers, measured on real git in the test beside the hook rather than reasoned about. A prune removes what a remote's configured refspec covers, by default `+refs/heads/*:refs/remotes/<name>/*`, so a destination inside that namespace is removed by `git fetch --prune <name>` and until somebody runs one it reads exactly like a branch the remote still has, which is the worse half in practice, since a count of that remote's merged branches counts it and the ancestry walk behind the count pays for it. A destination anywhere else, another tracking namespace or a name invented at the top, is removed by neither `git fetch --prune` nor `git remote prune`, ever. The first version of this hook said the harsher sentence for both cases and its own test refuted it, so the refusal now reads this repository's own remotes and says which of the four answers applies, never a guess. In the repository this was measured in, 4,761 such refs had gathered, 2,245 of them from one wildcard fetch, and listing the merged ones took 2.09 s against 0.084 s for the remote's own refs alone. ⛔ And the discriminator is not where the ref lands, it is whether a configured refspec covers it, source as well as destination. `git fetch origin +refs/heads/master:refs/remotes/origin/master` is the remote's own default refspec spelled out for one branch, a documented idiom, and the ref it writes is refreshed by every later plain fetch and protected by a prune, while `+refs/pull/7/head:refs/remotes/origin/pr-7` lands in the same namespace covered by nothing. Both are prunable, so prunability cannot tell them apart, and the first version of this hook refused them with byte-identical words. It now reads the repository's own `remote.<name>.fetch` patterns and refuses only a refspec none of them maps, so configuring the refspec the refusal offers also silences it, which a test holds. A destination under `refs/heads/`, `refs/tags/`, `refs/notes/` or `refs/replace/` goes through, because each has a command that shows it and a person who can remove it, and so does a plain local branch name, a remote given as an address or a URL, a push, a fetch with no destination, which is almost every fetch, and anything at all in a folder whose patterns cannot be read, since a hook that cannot tell must not refuse. The refusal names both ways through, since one with no way through is routed around: fetch the source alone with `--no-write-fetch-head`, which writes no ref and no FETCH_HEAD, and read each sha from `git ls-remote`, both taking many refs in one call where a wildcard would have been, or add the refs to the remote's own refspec so a prune keeps that namespace clean. It takes no configuration. `stray_refs.check`, `strays`, `destination`, `owned`, `tracking_namespace`, `configured_remotes`, `configured_refspecs`, `covered` and `fate` are the parts.
- A GraphQL read whose request the network never carried is sent again, where before only an HTTP status was. The retry read `HTTP 502`, `503`, `504` and a refused stream, and the failures that actually arrive are mostly below HTTP, so each of those ended the whole pass it was in. Measured over one log of a sync that runs every five minutes, of 21 failures at one call site 12 carried no status at all, a connection, read or TLS handshake that timed out, a body `gh` could not parse (`unexpected end of JSON input`), and GitHub's own internal error, which answers with a reference to quote when reporting it. None of the 12 was sent again, while the 8 with a gateway status were and 1 was a credential the retry rightly leaves alone, since asking twice with the same token answers the same way. A read can always be asked twice, so all 12 shapes are now retried for a read. ⛔ A WRITE KEEPS THE NARROW RULE, because a timeout says nothing about whether the mutation reached GitHub and a second createIssue is a second issue, so a write is still sent again only when no server took it (503) or the stream was refused. `project_board.DROPPED_READ` is the part, and `_try_again` now answers per direction rather than by one expression.
- `no-restore` refuses a command that would overwrite a file git cannot bring back, and `claude-ops hook no-restore` runs it. Some programs write a file of their own choosing with no path on the command line and no question asked, and an `init` step is the usual shape. When that file is hand-written and no repository tracks it, one such command is an irreversible loss, and a quiet one, because the file is still there with other contents. Measured on a tool whose own warning says to run its init step: it wrote its 453-byte default over an instruction file loaded into every session, a sentinel line in that file was gone afterwards, and it asked nothing. The hook reads the Bash call's command line, finds every simple command on it (after `&&`, inside a pipeline, on a later line) and refuses when a rule's words stand at the start of one and at least one file that rule names exists and is not tracked by git. A file git tracks goes through, since a checkout brings it back, so the rule narrows itself to the case that cannot be undone. A folder that is no repository at all counts as unrecoverable too, because git answers that with a code rather than an error, while a git that cannot be run at all lets the command through. A copy kept outside git, a dated one beside the file or one published somewhere else, is insurance rather than history and does not count, since it leaves the loss recoverable by hand and never by a checkout. A rule's `command` is matched by the program's base name with leading assignments and wrappers stepped over (`VAR=x env -u A sometool init -g` matches `sometool init`), while another subcommand and a longer word do not, so a step that only prints something is left alone. The refusal names the file, says git does not track it and adds the rule's own `message`, which is where the deliberate route belongs, because a refusal with no way through is one people route around. Rules are in `--config`, `CLAUDE_OPS_NO_RESTORE_CONFIG` or `~/.config/claude-ops/no-restore.json`; with none nothing is refused. `no_restore.check`, `rules`, `program`, `begins_with`, `restorable` and `at_risk` are the parts.
- The rewrite step leaves a command alone when that command's own output is consumed on the same line, by a pipe into another program or by a redirection of stdout to a file. The proxy's whole value is a shorter output for the session to read, and in both of those shapes the reader is a program or a file instead, so the rewrite saves nothing there and changes the bytes that reader receives. It is silent and it is measurable. `git diff A B | grep "^+" | grep -v "^+++" | wc -l` counted 135 added lines through the proxy where the diff holds 182, which `git diff --numstat` confirms, and a redirection of the same diff wrote 54,346 bytes into the file where the command's own output is 162,689, so a later read of that file counted 283 added lines where the diff has 1,123. Nothing in the output says it was rewritten and the error is low, which is the direction a reader does not question, and that shape is how a session checks a rebase, counts failures or compares two diffs. `||` is an or-list and not a pipe, a `|` or `>` inside quotes or escaped by a backslash is an argument, and `2>` and the other stream numbers move stderr and leave the output where it was, so all of those are still rewritten. A redirection the step cannot read as another stream's counts as this command's own, because a rewrite skipped for no reason costs a few tokens while one taken before a counter costs a wrong number. Two of the step's inherited test cases change with it, since a plain grep piped into another grep now runs as written. `rtk_rewrite.output_goes_elsewhere` is the part.
- `heavy`'s hour note says how far the most memory free of the whole wait got from what the job asks, and the whole number of GB a job could ask for instead and start at once. A gate half a gigabyte out of reach for an hour reads exactly like one that is hopeless, and the two want different repairs, the first a job asking for more than it needs and the second a machine with no room. The words give the gap and the figure to declare, and they never say that waiting cannot help, because a gate log does not support that sentence. Measured over nine days of one busy machine, of the eight waits that reached the hour note every ceiling was 0.1 to 0.6 GB short of the ask, and five of the eight ran anyway, three of them within 46 minutes of the note and two after six hours, so a line telling a job to stop waiting would have been wrong in five cases out of eight and no stretch of time is chosen here. A ceiling that has reached the ask says the other thing worth knowing instead, that memory has been free during this wait, so the gate can open again with nothing on the machine changing and something else held the job at the moment it looked. The words also name which measure of free memory the gate counts (free and reclaimable), so a reader who meets another program's reading of the same machine can tell the two apart rather than trusting whichever they saw first. `status` says the same sentence beside a waiter, with the ask that waiter itself recorded (`ask_gb` in its ticket's gate record, beside `most_free_gb`) and never the reader's own `HEAVY_MIN_FREE_GB`, which belongs to another process and may be a different number, while a ticket written before that was recorded still says only the ceiling it knows. `heavy.ceiling_words` is the part.
- `union <worktree> --replay-risk FILE` reads a branch before any rebase and says whether a rebase can leave a line of a union-merged file twice. A union keeps both sides of a block, so when a later commit of the branch rewrites or removes a line one of its own earlier commits added, the replay keeps the earlier version and the later one and the branch arrives with that line twice, with no conflict to settle and nothing for a person to see. A merge compares the two end states and replays nothing, so `git merge-tree` of the same two heads is clean and the branch's own end-to-end diff can read as a pure addition, which is why a gate that reads the heads is blind to this whole class and the doubling appears only at the rebase. It lists every commit of `<base>..<head>` that changes the file with its added and removed counts, exits 1 naming both commits and the line when one of them removes what an earlier one added, and asks for that file's commits to be squashed, since one commit cannot hold two versions of a line. A branch whose commits only add lines cannot double one, and the report says so rather than staying silent, so a reader is told why their case is safe. A line that came with the base is left out, being the question a three-way read of the two heads already answers, and so are blank lines. `--base` and `--head` name the two ends (`--head` so a branch can be read without checking it out), merge commits are left out because a rebase replays the commits under them, and for the same reason the read asks git for the full history, which would otherwise leave out a commit whose change a merge did not keep. `union.commits_touching`, `union.replay_doubles` and `union.report_replay_risk` are the parts.
- `container-recreate` reads a published port as answering only when the connection stays open for half a second or brings data. Docker Desktop's port forwarder accepts a connection on a published port whenever the container runs and closes it at once when nothing inside listens, so a connect alone passed a new container whose program had not started, and the restore path was reached only when the container exited. A container that was stopped is now made again stopped. The new one runs for its check and is stopped after it, and on a failure the old one is put back without being started. Before, both ways left it running. The check still cannot tell the right program from another one listening on the same port, since a server that waits for the client to speak (postgres, HTTP) looks the same as any other that accepts and waits. A health check in the image is the way to check more. `container_recreate.READ_S` is the time a connection must stay open.
- `container-recreate <name>` and `claude_ops.container_recreate.recreate(name)` create a container again from a fresh pull of its image reference, keeping how it was made and its data. `docker restart` starts the same image again, so a release published under the tag reaches the container only when it is created again, and a container made with a plain `docker run` records nothing of how it was made, while its data often sits on an anonymous volume a new `docker run` would not mount. It reads the container and the image it runs, pulls the reference and stops when that still names the same image. Otherwise it stops the container and renames it to `<name>-old`, runs a new one with the same name, published ports, environment the user set (not the image's defaults), shared memory size, restart policy, labels, network, command, log settings, tmpfs mounts, `--rm`, `-i`, `-t` and every mount (a volume by its name, a bind mount by its path), and checks it answers (its health check, else a TCP connection to its first published port, else still running after 5 s). Then it removes the old container, whose volumes stay, or removes the new one and starts the old one again. A container a compose project manages, a leftover `<name>-old`, and one with any setting the new container would not get are refused before anything is touched, naming each. That check is a list of what is accounted for, not of what is not. Every field of the container's settings is copied, docker's own default, the image's own value, or refused by name (a memory limit, ulimits, added capabilities, extra hosts, a stop timeout, its own entrypoint, user, working folder, stop signal or health check, a second network, a fixed address), so a field docker adds later is refused rather than dropped without a word. `container_recreate.unaccounted` lists them. `outcome` is unchanged, recreated, restored, refused, failed or broken, and every docker call takes the caller's `env`. `container_recreate.plan`, `unaccounted`, `answers` and `recreate` are the parts.
- This repository's own fork guard workflow passes `--hosted-only` and pins the lint to the commit that added it, so the rule is stated in the workflow a reader opens as well as checked by CI from the working tree. A copy of that workflow in another repository carries the flag with it, and a repository that moves its pin to an older commit of the lint will see the flag refused outright rather than ignored, since the command parses its arguments strictly.
- `fork-guard --hosted-only` also reports a job whose `runs-on` the workflow file does not fix as a runner GitHub hosts. A repository anyone can read wants its jobs hosted, because a pull request from a fork would otherwise run on a machine of the project's own, and the shape that asked for this check is not the word `self-hosted` but a value left open: `runs-on: ${{ vars.RUNNER || 'ubuntu-latest' }}` reads as hosted in the file while a repository variable set once sends every job of that repository elsewhere, with nothing in the workflow changing to say so. A plain hosted label passes, a label of any other kind and a list or map of labels are reported, and an expression passes only when it reads the job's own matrix and every value there is a hosted label, since then the file still says which runners the job can use. A job that calls another workflow has no runner of its own and is not checked. The flag is passed in a repository's own workflow rather than decided from the event, so the file states the rule and the same command can be run by hand before a push; an expression that is empty on an event without that payload would turn the check off while still looking green. `fork_guard.hosted_runner`, `not_hosted` and `scan(..., hosted_only=)` are the parts.
- `runtime_check.stale_mappings` also leaves out files under `/private/var/db/` and `/var/db/`, kept with `/Library/Preferences/` in the new `SYSTEM_DATA`. macOS rewrites the data there while nearly every process maps it (analyticsd's `events.allowlist` is one), so a program that mapped it during a rewrite read as running a removed library.
- `accounts.refresh_ends(login)` says when a saved Claude login's refresh token stops being accepted, from its `refreshTokenExpiresAt`, and `accounts.renewable(login, now)` whether a renewal can still give it a new access token. Renewing the access token does not move that time, and after it the token endpoint refuses the refresh token, so only a new sign-in makes a new login. A caller that reads the time can ask for that sign-in a day or two before it, instead of learning of it when every session using the login stops. `renewable` is None, never True, for a login that holds a refresh token but does not say when it ends. `accounts.describe(login, now)` gives what a person may read about a login (whether there is one, when its access and refresh tokens end, and whether it is renewable) and never a token. A time field holding a number no date can hold (1e20, infinity, NaN) reads as no time, so a corrupt login never stops a status read.
- `heavy` caps a job started under a hold. A process that takes the slot with `hold --pid` and then starts a heavy job of its own (a step of a CI job, or a daemon that takes the slot before it starts its work, so that a give-up of `--max-wait` leaves nothing started) had that job run its command directly, with no memory cap, no `--max-hold` and no end of what it left running, because a job inside a holder was taken to be inside another heavy job, whose cap counts it. Nothing samples a hold's work. Such a job now takes no slot and waits for no turn, as before, and runs like any other job, in its own session under the memory cap and its `--max-hold`. It is given the holder's pid as `HEAVY_HELD`, so a heavy call it makes runs at once inside it, and its memory samples are written for the holder's pid, so a waiter reads what the slot's work takes. A job inside another heavy job (its `HEAVY_HELD` names the holder) still runs at once in that job's process group. `heavy.job_env(..., held=)` is the part.
- `turns.assign(..., small=)` can give the short place to the smallest short waiters first. Served by class and place, a job of one test waited behind an older short job of fifteen that keeps the short place for several minutes. With `small` from 1 to `short`, a short waiter of at most `small` units goes ahead of bigger short ones that have not waited `jump_s`, oldest first within each size, and a bigger one that has waited `jump_s` goes next whatever smaller one comes after it. A waiter that cannot say its size is never in the short line. `small=0`, the default, keeps the order by class and place. `turns.short_order` gives the short waiters in that order, so a caller can say where a waiter stands.
- `log-cap FILE...` and `claude_ops.log_cap.cap(path, max_bytes=, keep_bytes=)` cut any log that a program holds open for appending when it is over a size, keeping its last part in `<log>.1` and emptying the log in place, while the program runs. This is the cut `adb-log` made, moved out of `adb_log` so it serves every such log, not only the adb server's. `claude_ops.adb_log.cap`, `Capped` and `tail` are still there and are now `log_cap`'s, and `adb-log` works as before.
- `rescan <pr>` runs a check again when the app that made it says it could not complete, instead of reading it as a finding. Some scanners end a check run as `neutral` both when they found something and when they could not finish their scan, and only the run's title tells the two apart, so a gate that reads every neutral run as red stops on a scan that never ran and reports a finding that does not exist. GitHub refuses a re-request of a check run from anyone but its app, and most apps scan again when the pull request is closed and reopened. When every check that did not pass on the head is a completed neutral run whose title matches `could not complete` (or `--title <regex>`), `rescan` closes and reopens the pull request once, waits for a new run of each such check (`--timeout`, 30 minutes), and judges the new runs: 0 they passed, 3 one did not, 5 one could not complete either, 2 not done at the timeout. A neutral run with any other title is a finding, and nothing is closed for it, nor when another check failed (exit 1). Before closing it lists the open pull requests based on the head branch and reads them again after the reopen, and its line says whether they are still open on it. `--head <sha>` acts only on that head (exit 8 otherwise). Its line names the run ids before and after. `rescan.rescan`, `rescan.plan`, `rescan.incomplete`, `rescan.runs_on` and `rescan.based_on` are the parts.
- `stale-status` reads two more ways a background call loses a gate's status. `exit "$rc"` went through for any variable, so `gh pr checks 12 --watch; echo x; rc=$?; exit $rc` passed while it reported `echo`'s 0. It now goes through only when the variable was saved with `rc=$?` (or `local rc=$?`) straight after the watch. A watch in the body of a `for`, `while` or `until` loop is refused unless `|| exit 1` after it or `set -e` before it ends the loop at the first failure, because a loop gives only its last round's status, so a red check before a green one was reported as a success. `stale_status.saved_status` and `hides(..., in_loop=)` are the parts.
- `stale-status` refuses a Bash call run in the background that hides a gate's exit. A background call is reported by the status of its last command, so `gh pr checks 12 --watch; echo "rc=$?" >> log` or `gh pr checks 12 --watch | tail -5` was reported as a success while the checks were red. The call is refused when another command runs after the gate, its output is piped without pipefail, or `||` runs anything but a failing exit. The watch alone or last, joined with `&&`, in a condition, after `set -e` or `set -o pipefail`, followed by `|| exit 1`, or ending in `exit "$rc"` goes through, and so does every foreground call. In a month of one machine's session transcripts, 271 of 272 background calls that ran `gh pr checks --watch` or `gh run watch --exit-status` lost its status this way and none ended with `exit "$rc"`. `commandline.parse` gives each command the operator after it (`after`). `stale_status.background_refusal`, `hidden_gate`, `GATES` and `commandline.parse`'s `after` are the parts.
- `filemap` maps a folder tree and finds the files that answer a need, from paths and names alone. `walk(root, skip=)` gives one row per file (relative path, size, modified time, extension) without following links, and `signature(rows)` is a cheap reading (count, total size, newest time and a digest of every path, size and time) that changes when a file is added, removed, renamed, moved or edited, so a caller can rebuild its map only when it must. `find(rows, need, rules=, limit=)` ranks the rows for a need written in plain words, counting each need word found in a file name or a folder name and the folder and name words of the caller's own `rules`. Among files that match equally it prefers a format that can be sent (a PDF, then a picture, then a word processor file, then raw camera files), then the shorter file name and then the newest. When a save holds the lock longer than half of `meter.READ_HOLD_S` (1 s) the next piece is half as large, and when it takes under an eighth of it the next is twice as large, up to `meter.PIECE_ROWS_MOST` (8000). A build tool can start its worker in a session of its own (with setsid), so the worker is no longer in the job's group, and the cap read only the group. - The meter's collector answers 503 within `meter.COLLECT_WAIT_S` (8 s) of a request's start, counted on the clock, while another writer holds the store. The chats in use are the largest files, and reading a 100 MB transcript whole on each change took about a second. `sessions.rc_url` reads the same way, and `sessions.live_folders` asks `lsof` once for every process instead of once for each
- The iTerm2 listings (`inject.iterm_sessions`, `inject.send_iterm`, `update.screen_of`) skip a window iTerm2 keeps in its scripting model after it closed, whose tabs cannot be read. One such window made every listing fail, so no iTerm2 session was found at all; an error after the session was found is still raised
- `update.background_agent` also sees a workflow's agents, which write one folder deeper (`subagents/workflows/<run>/`), and counts a workflow as running between its phases while its journal is recent and it has no final state file. A chat running a workflow no longer reads as idle, so a restart does not end the run halfway
- `update.files_seen(transcript, since=None)`: each file the conversation wrote (Write, Edit, MultiEdit) or read whole, with the time of that result. Check it before telling a chat that a file it loads has changed, because a chat that changed the file itself already knows. Compare with the file's modification time to see whether someone else changed it afterwards
- `update.unfinished_background(transcript)`: the background commands a chat started that never got a task notification, with their command text, so a chat resumed after a restart can start again what it still needs. `update.last_start(transcript)` gives when the newest instance started, to pass as `since`.
- `inject` sends only into an empty input line: a half-typed message, a question on screen or a screen it cannot read answers `not-ready` (exit code 5) and sends nothing. `--force` still skips the checks
- `update.screen_of` reads a tmux pane with its styles and `update.plain_screen` drops the suggested next prompt Claude Code draws dim in an empty input line, so `empty_prompt` no longer reads a suggestion as text somebody typed. `chat.pane_text(styled=True)` keeps the codes, and `update.TYPED` names the typed-text answer
- `update.resume_line(..., name=...)`: the chat's current name replaces the `-n`/`--name` (and a named `--remote-control`) it started with, so a restart does not undo a rename.
- `update.model_of` reads the model and effort level a chat last ran on from its transcript, and every restart and `chat.resume_command` pass them on (`--model`, `--effort`), so a model or effort chosen inside the chat survives a restart. A chat started with `--settings` keeps the model its settings file names
- `update.restart_into_tmux` moves a chat from an iTerm2 tab into tmux shown in that same tab, and `update.restart_tmux` restarts a tmux chat inside its own pane. Neither opens a window
- `update.ready` puts every check on a chat in one place, adds `update.background_agent` (a background agent keeps a chat busy), and names a question waiting for the person instead of calling the chat "working"
- `update.remote_control_of` and `update.title_of` read a chat's Remote Control state and title from its transcript, so a restart keeps Remote Control
- `update.front_app(bundle_id=True)` gives the bundle id of the app in front
- `config.descendants(pid, procs)`, every process under one, so a window can be traced to the chat whose process made it
- `chat.in_tmux`, `chat.plain_look`, `chat.attach_line` and `chat.server_context`. A plain tmux session passes the chat's title to the terminal tab, so the tab no longer reads "cd (tmux)"
- `chat.claude_command` and `chat.resume_command` take `settings`, a settings file for that chat alone (`--settings <file>`), and a restart keeps the flag
