# Changelog

## Unreleased

- `no-session-links` (`claude-ops hook no-session-links`, a PreToolUse hook): refuses a tool call that would put a link to a Claude Code session (a `claude.ai/code/` address), a `Claude-Session` trailer or the id of a session transcript on this machine into git, GitHub or a file inside a repository. On a `git commit` it also scans what the commit would record: the staged changes, the tracked changes for `-a` or when the same command runs `git add`, and the files such an add names (not staged yet when the hook runs), following `git -C`, the options before the subcommand and an earlier `cd`. A refusal names the file and line, never the id, and on anything unexpected the hook lets the call through
- `update.empty_prompt` no longer reads a question that is gone as one still asked. A dialog's words count only while no input line sits below them, so the echo Claude Code leaves of an answered or cancelled question (`⎿ · Where do you want to start?`) and Claude's own prose ("Do you want me to ship it?") no longer hold a session as "asking" until they scroll away
- `update.stop_shell(pid, procs, started=..., parent=...)`: stop one background shell a session left running (`forgotten_shells`) with every process under it, only while the pid still names that same process (its start time, and its parent when given), so a pid another program took since is never touched. SIGTERM goes to the processes under the shell first, and what still runs after `grace_s` gets SIGKILL
- `update.signed_out(screen)`: the line on a session's screen saying it lost its login or its Remote Control, when that is the newest such word on it. `update.question_unreachable(screen, seconds_since_input)`: a question on a signed-out session's screen while nobody has used the computer for `AWAY_S`, which no phone can reach. `update.ready(..., question_blocks=False)` lets such a question go, so a restart that brings Remote Control back is not held by a dialog nobody can answer
- `changelog` (`claude-ops changelog <old> <new>`): the pull requests merged between two commits, oldest first, read from the first-parent history so the commits inside each pull request are not listed. A merge commit is named by its pull request's title (the first line of its body), a squash merge by its subject without the `(#N)`, and a commit pushed straight to the branch by its subject with no number. `changelog.merged(old, new, repo, env=)` returns `Change(sha, title, number, branch)`; `changelog.web_url(remote)` gives a GitHub remote's https address
- `iterm.chat_tabs` and `set_tab_color` read None and False when iTerm2's Python API does not answer, instead of ending the program. The `iterm2` package raises SystemExit(1) when it cannot connect, which `except Exception` let through, so a scheduled job calling either function stopped on every run while iTerm2's API was unreachable
- `messages.last_said(path, before=None)`: the last text the assistant wrote in a transcript (before a time when given), read from the end in growing chunks, so a short message sent to a chat can carry what it answers
- `accounts.renew`, `usage` and `profile` send a User-Agent (`accounts.USER_AGENT`). The token endpoint is behind Cloudflare, which refused Python's default `Python-urllib/3.x` with 403 (error code 1010), so every renewal of a saved login failed while usage, on another host, still answered
- `tracebacks` (`claude-ops tracebacks`): the Python tracebacks in log files, grouped by exception type and deepest frame (`--prefer` picks frames in your own code), read from a byte offset so a scheduled pass sees each one once (`tracebacks.read_new(path, offset)` returns the next offset). A traceback still being written waits, a shrunk log is read from the start, a chain is one traceback, and interleaved output from two threads keeps what was complete
- `messages` (`claude-ops messages`): what the person typed into chats over any range, from any chats (by title, folder or session), with the conversation before and after any message (`--around <session>:<line>`). It reads queued messages (queue operations and `queued_command` attachments) as well as user records and folds the copies of one message into one, and leaves out text written by Claude Code, hooks, schedules, other sessions and programs that type into the terminal
- `remote.set_title(row, name, token)` and `remote.title(row, token)`: give a Remote Control session its title, and read it, through the sessions API Claude Code itself uses (`PUT /v1/code/sessions/<id>`), with the OAuth access token of the account that owns the session. No browser and no page are needed, and it works for every account whose login is at hand, whichever account a browser is signed in to. `remote.NOT_FOUND` and `remote.REFUSED` name the two failures a caller can act on; `remote.api_id` turns a list row into the API's id. `accounts.login_for(account, items)`: the saved login among keychain items whose profile is a given account
- `iterm.restart_app()`: restart an iTerm2 that stopped answering while its terminals stay. With session restoration through iTermServer the terminals belong to the server, so the app is stopped (SIGKILL) and opened again, and it reconnects to them. Refused, with nothing stopped, unless one iTerm2 and one server run, the server holds the terminals and the app holds none. Returns the outcome and how many terminals the server held before and after; `iterm.Processes` is the part a test replaces
- `remote.remote_session(transcript)`: the Remote Control session and the account that owns it (`{"row", "account"}`). `rename_js(row, name, account=...)` checks which account the page is signed in to first and answers `remote.OTHER_ACCOUNT` (with `signed_in`) instead of waiting for a row the list cannot show, since the Code list shows only the signed-in account's sessions. `remote.NOT_LISTED` is the answer for a missing row. `remote.account_js()` reads the page's account on its own, to compare before any rename
- `adb.reach(..., env=)`: the environment every adb command runs with, like every other function here that starts a process
- `adb-reach` (`adb.reach(host)`): reach an Android device over adb again after a restart undid `adb tcpip`. It tries the fixed port (5555), and when that refuses it scans the address for the wireless-debugging port (`adb.open_ports`), connects there and runs `tcpip`, so the fixed port listens again. `keep_wireless` turns wireless debugging back on when `tcpip` turned it off, and `adb.wireless_on` reads or sets it. Open ports that are not adb are disconnected, so no offline entry stays behind
- `heavy`: a job that fails the same way `HEAVY_REPEAT_FAILS` (3) times in a row (over the memory cap whatever it reached, at its `--max-hold`, or with one exit code) says so on its last line with `AGAIN:`, and with `--notify` tells its chat, at the third failure and each time the count doubles. `status` lists every such job from the last `HEAVY_REPEAT_HOURS` (24). Each `done/<pid>.json` now keeps `end` and `how`, and `heavy.failing()`, `heavy.streaks(records)` and `heavy.failed_how(record)` give the same to a reader of `HEAVY_DIR`
- `update.forgotten_shells(pid, procs, screen, now)`: the commands a session left running in the background while its prompt sits empty, older than `older_than_s` (an hour by default), each with its pid, age and command (`update.shown_command` takes the command out of Claude Code's shell wrapper). A request to finish background work in general did not get such a command stopped, because the session could not tell which task was meant. `idle` now names the oldest shell it waits for: "it is running a command (pid N, for 4h47m)"
- `restack`: rebuild a stack of one-commit branches on a new base, one worktree per branch, bottom first, settling add-only conflicts with `union` (`--ordered`, `--journal`, `--set` as there). It stops at the first conflict union refuses and leaves that rebase for a person. `claude-ops restack <base> <worktree>...`
- `detach`: start a command in its own session, with its output appended to a log, and print its pid (also its session and group id), so a job a chat starts outlives the chat. `claude-ops detach --log FILE [--cwd DIR] -- COMMAND...`; `detach.detach(argv, log, cwd=, env=)` from Python
- `go_public.go(repo, terms=..., allow=..., reference=...)`: make a repository public with a check for private terms already in place. It scans every tracked file and commit message (reporting where a term matched, never the text) and refuses a private repository that carries one. It sets the secrets that hold the terms, copies the check's workflow from a reference repository through a pull request that must pass it, and verifies both before it changes visibility. `check_only` stops before the last step, and `after(repo)` runs at the end. `go_public.refresh` sets the secrets again on every public repository that runs the check, after the lists change. `go_public.sh` runs a command in its own process group and kills the whole group on a timeout
- `environ.child_env(path=..., keep=..., add=...)`: the environment to start a child process with, built from nothing. Only a short list of variables a command needs (`BASE`, each with its reason), the ones named at the call site, and the PATH the caller gives. `REDIRECTS` names the variables that redirect a command rather than inform it (`PYTHONPATH`, `GIT_DIR`, `LD_PRELOAD`, `TMUX` and others); asking to keep or set one raises ValueError
- `ssh.run`, `ssh.copy` and `ssh.peer_online`: one way to run a command on another machine and copy files there. A host that could not be reached always comes back as a CompletedProcess with `UNREACHABLE` (255) and the reason in stderr, never an exception; a password goes on stdin, never on the command line; `peer_online` asks Tailscale whether the host is online in its own view. Each takes `env`
- `union --set FILE` (`settle_tree(sets=...)`, `settle_set`): a ledger whose entry lines are an unordered set merges three ways, keeping every line either side added and dropping every line either side removed, wherever they sit, so an entry added beside one the other branch removed no longer stops a rebase; a Python ledger must still parse
- `owners.most_specific(subject, owners, kind="like"|"glob")`: the owner whose pattern matches a subject with the most literal characters, so an exact address beats a wide one; SQL LIKE patterns or shell globs, a tie going alphabetically
- `accounts.write_item` sends the login as quoted text instead of hex: `security -i` cuts a line longer than 4,032 characters, and a real Claude login in hex is longer, so it was saved cut. A login too long even as text raises ValueError and is never written on a command line
- `accounts`: read and write a keychain login item (the secret on stdin, never a command line), an account's usage and profile, renewing a saved login, the usage-limit stop in a transcript (`limit_hit`), and `choose`, which picks the account to switch to: one usable now, only when the one in use is spent
- `remote`: which Remote Control session a transcript belongs to (`remote_id`, its newest `bridgeSessionId`, as the claude.ai Code list names it) and the page script that renames that row and reads the title back (`rename_js`), since a resume keeps the session's old title and `/rename` does not change it. `update.continue_after_error`: the pure rule for telling a session stopped on a transient API error to continue, once per error, only while recent, at most a few times an hour
- `iterm`: find and tidy iTerm2's windows through AppleScript. `windows` (id, tab count, frame, title), `dead_windows` (frames iTerm2 closed but left on screen), `close_empty_window` (only a window that holds no session), `set_bounds` (read back, for a window yabai has lost), `window_of_session`, `session_of_tmux_pane`, `window_of_ttys` with `tmux_client_ttys` (a tmux chat's window by its client's terminal, never by title). Each window is read inside its own `try`, and a listing that could not be taken is None
- `config.login_digest()` fingerprints the account Claude Code is signed in to (the account and organization ids in `~/.claude.json`), and `snapshot()` includes it. A running chat keeps the login it started with, so a fingerprint that changed after a chat started means the chat needs a restart to use the new account
- `claude-ops stall <path>` (`watch.stall`, `watch.stall_check`) waits on a session's transcript, a folder of them, or any file or folder a job writes, and says whether the session finished its turn (exit 0), a done file was written (0), the path is gone (0), the session stopped on an API error such as a usage limit (1), nothing changed for `--minutes` (1, stalled, with what the last record was waiting on), or it was still changing after `--max-hours` (2). A folder finishes when every transcript in it ended its turn. The clock and the sleep are arguments, so a test does not wait. `update.last_message(transcript)` gives the newest record in which the conversation moved, read from the end past the bookkeeping Claude Code appends after a turn, and `update.last_activity` uses the same rule for which records count
- `claude-ops heavy` (`heavy.run`, `heavy.wait_turn`): one heavy job at a time on a shared machine, taken in turn across chats, gated on free memory, swap and disk, run under a memory cap on its process group, with `hold`/`release` for CI runners, `--max-hold`, `--notify` through `HEAVY_NOTIFY`, and each finished job's peak memory kept in `HEAVY_DIR/done`. `footprint.footprint_gb` reads a process's memory footprint (top's MEM) with proc_pid_rusage, and answers None off macOS
- `chat.claude_pid()`: the Claude Code process a hook or any child of a chat runs under, found by walking up the process tree to the first `claude` (with `chat.parent_of` reading one step through `ps`, and a `parent` stand-in for tests)
- `claude-ops layering <root> --package <pkg> --marker <import>` (`layering.candidates`) lists the modules of a project that reach none of the given markers through their imports, followed all the way down the project's own modules. In a private project built over public packages, a marker is an import that means "this uses the private side" (its database driver, the module that writes its records), so a module that reaches none works without it and is a candidate to move into a package. `reaches` gives the import chain that ties a module to a marker. It is meant for a test in the private project that keeps a reviewed list of the modules that stay, with their reasons
- Four repository tools, each a command and a module: `claude-ops union` (`union.settle_tree`) settles a rebase conflict where both sides only added lines and refuses every other, with JSON merged by key, `--ordered` files listed once and `--journal` files kept append-only; `claude-ops secret-shapes` (`secret_shapes.scan`) refuses commits that add a line of a shape a secret scanner flagged before, from a shapes file the project keeps, reading every commit as the scanner does; `claude-ops mutate` (`mutate.run_mutations`) writes generated or hand-written mutations into a copy of a worktree and lists the ones the test command lets pass; `claude-ops plan-apply` applies a written plan's Write and Edit steps exactly. Every function that runs git or a test command takes `env`
- `iterm` and `claude-ops tab-colors`: in every iTerm2 window that holds two or more chats (tabs showing a tmux session named `claude-*`), each tab gets a color no other tab in that window has. A color the user set is kept, a chat can take back the color it had before (`assign`'s `remembered`), and new colors come from `PALETTE`. Reading and writing go through iTerm2's Python API (`pip install 'claude-ops[iterm]'`, and the API switched on in iTerm2's settings)
- `update.is_waiter` also counts a report that sets a variable from a substitution and tests it (`L=$(ls -t x | head -1); [ -n "$L" ] && grep ...`), and `{ ... }` groups: `[`, `test`, `true` and `false` read, an assignment's value is checked as its substitution, and a `|` or `;` inside a `$( ... )` no longer splits the command around it
- `update.is_waiter` counts a report after the wait that only reads: a `for NAME in ...` loop with its `do`/`done`, an `if`/`then`/`else`/`fi`, and the `gh` subcommands that read (`GH_READS`: `pr view`, `pr checks`, `pr list`, `run view` and the like). A chat whose waiter reported a few pull requests' states once its log ended was never idle, so it was never restarted. Every `$( ... )` is now checked as a command of its own, and a backtick is refused: an `echo "$(...)"` used to pass whatever the substitution ran
- `update.stopped_on_api_error(transcript)`: the transient API error a conversation stopped on, when its newest message is Claude Code's `isApiErrorMessage` record whose text starts with "API Error:" ("Connection lost mid-response", a closed socket, the API server out of reach or limiting requests) and nothing was typed or queued after it. The session then waits at its prompt as if its turn had finished, so a supervisor can send it a short message to continue. Usage limits, a prompt that is too long, billing and an expired login are not transient (`NOT_TRANSIENT`), since asking again cannot help
- `claude-ops merge <number>` (`merge.merge_when_green`) merges a pull request only when every check on its current head has passed, waiting for checks still running. It reads the checks from gh's JSON, refuses a pull request with a failed check or with no checks at all (`--allow-no-checks` to merge one anyway), and merges with `--match-head-commit`, so a push between the check and the merge is refused by GitHub. Waiting and merging as two steps had let a pull request be merged with two test jobs red
- `update.idle` and `update.ready` look through background shells that only wait: a loop whose body is `sleep N` (`until <test>; do sleep 60; done`), followed by nothing or only commands that read and print, sitting in its `sleep` right now (`is_waiter`, `waiting_shells`, `command_lines`). Such a shell loses nothing when its chat restarts, because the next instance is told which background commands did not finish. A chat that kept a few of these running was never idle, so it was never restarted. `ready` reads the command lines itself; `idle` uses them when given
- `chat.diagnose` looks for a start-up question only in the last lines of the screen, and never while Claude Code's input box is there (`chat.input_box`). It matched the words anywhere, so a chat at its prompt whose conversation quoted "Yes, I trust this folder" read as stuck on the trust question, and `chat.at_prompt` never saw it ready
- The session index follows a conversation that moved to another folder: every record names the folder it ran in, and the newest one is the entry's `cwd`, on a full read and on an incremental one. It kept the folder of the first record, so a chat resumed elsewhere was listed under the folder it had left
- `sessions.build_index` writes the cache through a temp file of its own: with one shared name, two processes indexing at once renamed each other's file away and the second failed
- The test suite never reaches the tmux server of the person running it: a session-wide fixture unsets `$TMUX` and gives tmux a private `TMUX_TMPDIR` under /tmp. Inside a tmux pane, tmux follows `$TMUX` before `TMUX_TMPDIR`, so a test's `tmux kill-server` cleanup ended the real server and every session in it
- `inject.send_tmux` loads the text into the tmux buffer through stdin (`load-buffer -`). It passed the whole text as one `set-buffer` argument, and tmux refuses a command longer than about 16 KB with "command too long", so a long message never arrived and the error text was all the sender got
- `update.tools_held(transcript)`: the deferred tool definitions a conversation holds now, each tool as its newest load since the last compaction recorded it, with its description and argument names. A resumed chat keeps those until it is compacted, so a restart does not give it an argument a server gained in the meantime. Compare them with the server's tools before telling a chat its tools are current
- `update.restart_iterm` and `update.restart_tmux` (when it builds the resume line itself) pass the chat's current title as `name`, so a chat renamed after it started comes back under its new name. They passed the start flags' `-n`, Claude Code wrote it back as the chat's title, and the rename was undone. `update.title_of` and `update.remote_control_of` read the transcript from its end, so a long one is not read whole (two seconds for a 1.8 GB transcript, now a few milliseconds)
- The session index reads a transcript that grew only from where its last read stopped, and writes its cache only when something changed. The chats in use are the largest files, and reading a 100 MB transcript whole on each change took about a second. `sessions.rc_url` reads the same way, and `sessions.live_folders` asks `lsof` once for every process instead of once for each
- The iTerm2 listings (`inject.iterm_sessions`, `inject.send_iterm`, `update.screen_of`) skip a window iTerm2 keeps in its scripting model after it closed, whose tabs cannot be read. One such window made every listing fail, so no iTerm2 session was found at all; an error after the session was found is still raised
- `update.background_agent` also sees a workflow's agents, which write one folder deeper (`subagents/workflows/<run>/`), and counts a workflow as running between its phases while its journal is recent and it has no final state file. A chat running a workflow no longer reads as idle, so a restart does not end the run halfway
- `update.files_seen(transcript, since=None)`: each file the conversation wrote (Write, Edit, MultiEdit) or read whole, with the time of that result. Check it before telling a chat that a file it loads has changed, because a chat that changed the file itself already knows. Compare with the file's modification time to see whether someone else changed it afterwards
- `update.unfinished_background(transcript)`: the background commands a chat started that never got a task notification, with their command text, so a chat resumed after a restart can start again what it still needs. `update.last_start(transcript)` gives when the newest instance started, to pass as `since`.
- `inject` sends only into an empty input line: a half-typed message, a question on screen or a screen it cannot read answers `not-ready` (exit code 5) and sends nothing. `--force` still skips the checks
- `update.screen_of` reads a tmux pane with its styles and `update.plain_screen` drops the suggested next prompt Claude Code draws dim in an empty input line, so `empty_prompt` no longer reads a suggestion as text somebody typed. `chat.pane_text(styled=True)` keeps the codes, and `update.TYPED` names the typed-text answer
- `update.resume_line(..., name=...)`: the chat's current name replaces the `-n`/`--name` (and a named `--remote-control`) it started with, so a restart does not undo a rename.
- `update.model_of` reads the model and effort level a chat last ran on from its transcript, and every restart and `chat.resume_command` pass them on (`--model`, `--effort`), so a model or effort chosen inside the chat survives a restart. A chat started with `--settings` keeps the model its settings file names
- `update.restart_into_tmux` moves a chat from an iTerm2 tab into tmux shown in that same tab, and `update.restart_tmux` restarts a tmux chat inside its own pane. Neither opens a window
- `update.ready` puts every check on a chat in one place, adds `update.background_agent` (a background agent keeps a chat busy), and names a question waiting for the person instead of calling the chat "working"
- `update.remote_control_of` and `update.title_of` read a chat's Remote Control state and title from its transcript, so a restart keeps Remote Control
- `update.front_app(bundle_id=True)` gives the bundle id of the app in front
- `config.descendants(pid, procs)`, every process under one, so a window can be traced to the chat whose process made it
- `chat.in_tmux`, `chat.plain_look`, `chat.attach_line` and `chat.server_context`. A plain tmux session passes the chat's title to the terminal tab, so the tab no longer reads "cd (tmux)"
- `chat.claude_command` and `chat.resume_command` take `settings`, a settings file for that chat alone (`--settings <file>`), and a restart keeps the flag

## 0.4.0

- `claude_ops.config`: the installed Claude Code version, the version a running chat runs, and fingerprints of what a chat loads at start
- `claude_ops.update`: whether a chat may be touched, and `restart_iterm`, which restarts a chat in iTerm2 as the same conversation with its flags and permission mode
- `claude_ops.worktree`: a chat's own git worktree with the main checkout's local files and memory linked in
- `claude_ops.move`: move a conversation's files to another project folder, checked before any original leaves
- `chat.claude_command`, `chat.resume_command`, `chat.pane_owner`, `chat.at_prompt`, `chat.repo_name`, and `sessions.rc_url`, `sessions.pick`, `sessions.project_for`
- The skill covers all of it

## 0.3.0

- Every function that starts a process (tmux, osascript, pgrep, lsof, rg) takes an optional `env`, passed to the process. `None` keeps the inherited environment

## 0.2.0

- A main `claude-ops` skill, and more detail in chat-watcher, mentor and rover from the conversations they came from
- `claude-ops chat end`, which detaches iTerm2 before stopping the tmux session
- The rover harness no longer needs `timeout`, which stock macOS does not have

## 0.1.0

First release.

- `claude-ops sessions` and `search` find chats from every project folder
- `claude-ops inject` sends a message into a running chat in iTerm2 or tmux, with an append-only log
- `claude-ops chat` starts chats in tmux, answers the trust prompt by its words, and shows them in iTerm2
- `claude_ops.watch` for scheduled watchers that wake a chat only when something is new
- Skills chat-watcher, mentor and rover
- Hooks ask-what-you-need, context-check and context-mark
- `claude-ops slots` for Playwright profile locks, and `claude-ops restore` for chats that disappeared
